### Work Item 3.1: Brute Force Protection (REQ-SEC-05)

**Goal:** Create `login_attempts` table + `BruteForceService` that tracks failed login attempts per-user and locks accounts after 5 failures for 15 minutes.

#### Implementation Notes

```typescript
// brute-force.service.ts
const MAX_ATTEMPTS = 5;
const LOCKOUT_DURATION_MS = 15 * 60 * 1000;
const WINDOW_MS = 15 * 60 * 1000;

@Injectable()
export class BruteForceService {
  constructor(
    @InjectRepository(LoginAttempt)
    private readonly repo: Repository<LoginAttempt>,
  ) {}

  async isLocked(userId: string): Promise<boolean> {
    const record = await this.repo.findOne({ where: { userId } });
    if (!record) return false;
    if (record.lockedUntil && record.lockedUntil > new Date()) return true;
    if (record.lockedUntil && record.lockedUntil <= new Date()) {
      await this.repo.delete({ userId });
    }
    return false;
  }

  async recordFailedAttempt(userId: string): Promise<void> {
    const windowStart = new Date(Date.now() - WINDOW_MS);
    let record = await this.repo.findOne({ where: { userId } });
    if (!record) {
      record = this.repo.create({ userId, failedAttempts: 1, lockedUntil: null });
    } else {
      if (record.createdAt < windowStart) {
        record.failedAttempts = 1;
        record.lockedUntil = null;
        record.createdAt = new Date();
      } else {
        record.failedAttempts += 1;
      }
    }
    if (record.failedAttempts >= MAX_ATTEMPTS) {
      record.lockedUntil = new Date(Date.now() + LOCKOUT_DURATION_MS);
    }
    await this.repo.save(record);
  }

  async resetAttempts(userId: string): Promise<void> {
    await this.repo.delete({ userId });
  }
}
```

Key notes:
- Lockout check happens **before** credential validation to prevent leaking user existence via timing
- On-read cleanup: `isLocked()` deletes expired lockout records as a side effect



> **Note (post-execution):** CSRF protection was originally planned here (Work Item 3.2) but later removed.
> The original research incorrectly applied session-cookie CSRF reasoning to a Bearer-token API.
> All API endpoints use `Authorization: Bearer` headers (not cookies), making CSRF structurally impossible.
> The `/auth/refresh` endpoint's httpOnly cookie uses SameSite=Strict, which prevents cross-origin cookie sending.
> Commit `092386a` removed the CSRF implementation (csrf.service.ts, endpoint, middleware, related tests).

### Work Item 3.4: Increase Argon2 Memory Cost (MAJ-06)

**Goal:** `HashService.hashPassword()` uses argon2 defaults with memory cost 19 (= 2^19 KiB = 2 MiB). Increase to `memoryCost: 37888` (~37 MiB) for production-appropriate resistance against GPU/ASIC attacks.

#### Files to Modify

| File | Required Changes |
|------|-----------------|
| `backend/src/auth/hash.service.ts` | Pass explicit `memoryCost: 37888` to `argon2.hash()` options. Keep `timeCost: 2` (default), `parallelism: 1` (default). |

#### Implementation

```typescript
// hash.service.ts — updated hashPassword
async hashPassword(password: string): Promise<string> {
  return argon2.hash(password, {
    type: argon2.argon2id,
    memoryCost: 37888,  // ~37 MiB (up from 2 MiB default)
    timeCost: 2,
    parallelism: 1,
  });
}
```

**Why 37888?** OWASP recommends minimum 19 MiB (memoryCost: 19456) for interactive logins and 37 MiB (memoryCost: 37888) for non-interactive operations. Password hashing during registration is non-interactive — user already waits for the response — so 37 MiB is appropriate.

**Why not use argon2 default?** Default is 2 MiB — trivially parallelizable on modern GPU hardware. 37 MiB forces attackers to use significantly more memory bandwidth, reducing throughput by ~18x.

#### Test Strategy

| Test | Approach | Command |
|------|----------|---------|
| Hash uses configured memory cost | Mock argon2.hash, verify options.memoryCost === 37888 | `pnpm test -- hash` |
| Hash still produces valid result | End-to-end: hash a password, then verify it with argon2.verify | `pnpm test -- hash` |

### Work Item 3.5: Fix Rate Limiting on Password Endpoints (MIN-04)

**Goal:** Tighten rate limits on sensitive password endpoints. Currently `forgotPassword` has no rate limit in code (the Wave 1 plan added `@Throttle({ default: { limit: 1, ttl: 60000 } })` but `forgotPassword` is a single endpoint — `default` may not apply correctly). `resetPassword` has no specific rate limit.

#### Files to Modify

| File | Required Changes |
|------|-----------------|
| `backend/src/auth/auth.controller.ts` | Add explicit `@Throttle()` decorators: `forgotPassword` → 3 requests per 60 seconds. `resetPassword` → 5 requests per 60 seconds. Both use `@SkipThrottle(false)` if endpoints are behind a controller-level throttle group. |

#### Implementation

```typescript
// auth.controller.ts — updated rate limits
@Post('forgot-password')
@Throttle({ default: { limit: 3, ttl: 60000 } })
@HttpCode(HttpStatus.OK)
async forgotPassword(@Body() dto: ForgotPasswordDto) { ... }

@Post('reset-password')
@Throttle({ default: { limit: 5, ttl: 60000 } })
async resetPassword(@Body() dto: ResetPasswordDto) { ... }
```

Note: The `@nestjs/throttler` `@Throttle()` decorator overrides the global config per-endpoint. The `default` key references the default throttle group.

#### Test Strategy

| Test | Approach | Command |
|------|----------|---------|
| forgotPassword rate limit | Call forgotPassword 4x in 1s (with valid emails) → 4th exceeds 3 req/60s → 429 | `pnpm test:e2e` |
| resetPassword rate limit | Call resetPassword 6x → 6th exceeds 5 req/60s → 429 | `pnpm test:e2e` |
