```typescript
// token-hash.service.ts
import { Injectable } from '@nestjs/common';
import { createHash, timingSafeEqual } from 'node:crypto';

@Injectable()
export class TokenHashService {
  hash(token: string): string {
    return createHash('sha256').update(token).digest('hex');
  }

  compare(token: string, hash: string): boolean {
    const tokenHash = createHash('sha256').update(token).digest('hex');
    const bufA = Buffer.from(tokenHash);
    const bufB = Buffer.from(hash);
    if (bufA.length !== bufB.length) return false;
    return timingSafeEqual(bufA, bufB);
  }
}
```

#### Test Strategy

| Test | Approach | Command |
|------|----------|---------|

| Compare matches correct token | `compare(token, hash(token))` returns true | `pnpm test -- token-hash` |
| Compare rejects wrong token | `compare('wrong', hash('correct'))` returns false | `pnpm test -- token-hash` |

#### CRIT-01: Soft-Delete Bypass Fix

The `UsersService.findByEmail()` and `findById()` methods currently use `withDeleted: true` (TypeORM `FindOneOptions`). This means soft-deleted users can still authenticate, refresh tokens, and perform actions.

```typescript
// users.service.ts — fixed findByEmail
async findByEmail(email: string): Promise<User | null> {
  return this.userRepo.findOne({
    where: { email, deletedAt: IsNull() },
  });
}

// users.service.ts — fixed findById  
async findById(id: string): Promise<User | null> {
  return this.userRepo.findOne({
    where: { id, deletedAt: IsNull() },
  });
}
```

**Impact chain:** This fix propagates to all callers:
- `AuthService.validateUser()` uses `findByEmail` — soft-deleted users can no longer log in.
- `AuthService.refreshAccessToken()` uses `findById` — soft-deleted users cannot refresh.
- `AuthService.forgotPassword()` uses `findByEmail` — soft-deleted users cannot request resets.

No other caller changes needed — all callers expect `User | null` and handle null appropriately.

#### Key Implementation Details

- `SessionService.createSession()`: hash `refreshToken` before `this.sessionRepo.create()`
- `SessionService.validateRefreshToken()`: hash incoming token before `findOne` where clause
- `AuthService.logout()`: iterate sessions, use `tokenHashService.compare(sessionToken, session.refreshToken)` instead of `===`
- `AuthController.revokeAllSessions`: fix `s.refreshToken === refreshToken` comparison to use `TokenHashService.compare()`
- `RefreshTokenGuard`: No change needed — passes raw JWT, `validateRefreshToken` hashes internally

### Work Item 2.4: Atomic Refresh Token Rotation (REQ-SEC-02, CRIT-02)

**Goal:** Fix the race condition in `refreshAccessToken()` — current code does `revokeSession()` then `createSession()` in separate operations. An attacker sending two concurrent refresh requests can create infinite sessions (both pass the guard, both find the old session valid, both create new sessions — now two valid sessions exist).

**Fix:** Replace the non-atomic revoke-then-create pattern with `SessionService.consumeSession()` that does `DELETE ... RETURNING` in a single statement. If 0 rows are deleted (session already consumed), abort with 401.

#### Files to Modify

| File | Required Changes |
|------|-----------------|
| `backend/src/auth/session.service.ts` | Add `consumeSession(sessionId: string, userId: string): Promise<Session | null>` — uses `repo.delete()` + checks affected rows, or raw query with `RETURNING`. Returns the deleted session or null if not found. |
| `backend/src/auth/auth.service.ts` | Update `refreshAccessToken()`: call `consumeSession()` instead of `revokeSession()`. If null returned, throw UnauthorizedException (token already consumed). Then create new session via `generateTokenPair()`. |
| `backend/src/auth/auth.controller.ts` | Update `refresh()`: pass sessionId, set new refreshToken cookie in response |
| `backend/src/auth/__tests__/session.service.spec.ts` | Add test for `consumeSession`: verify session deleted, verify returns null for already-consumed session |
| `backend/src/auth/__tests__/auth.service.spec.ts` | Update refresh test: verify `consumeSession` called, verify old session revoked atomically, verify new session created |

#### Key Details

- **Atomic pattern:** `DELETE FROM sessions WHERE id = :id AND user = :userId RETURNING *` — if two concurrent requests arrive, only one succeeds (the first one). The second sees 0 affected rows.
- TypeORM supports `delete()` returning affected count via `result.affected`. Use this for the atomic check. For full row data, use raw query or `findOne` before delete.
- **Alternative if RETURNING not needed:** Use TypeORM `delete()` and check `result.affected === 0` → throw. The old session data isn't needed for rotation — we just need to know it was consumed.
- `RefreshTokenGuard` already sets `request.user.sessionId` (line 46 in guard). No change needed.
- Controller now sets `refreshToken` cookie in response (wasn't doing this before — just returning `accessToken` in body).

```typescript
// session.service.ts — consumeSession
async consumeSession(sessionId: string, userId: string): Promise<boolean> {
  const result = await this.sessionRepo.delete({
    id: sessionId,
    user: { id: userId },
  });
  return (result.affected ?? 0) > 0;
}
```

```typescript
// auth.service.ts — updated refreshAccessToken
async refreshAccessToken(
  userId: string,
  sessionId: string,
  userAgent?: string,
  ip?: string,
) {
  const user = await this.usersService.findById(userId);
  if (!user) throw new UnauthorizedException('User not found');

  // Atomically consume old session — if already consumed, abort
  const consumed = await this.sessionService.consumeSession(sessionId, userId);
  if (!consumed) {
    throw new UnauthorizedException('Session already revoked');
  }

  // Generate new token pair (creates new session)
  const tokens = await this.generateTokenPair(user, userAgent, ip);
  return {
    accessToken: tokens.accessToken,
    refreshToken: tokens.refreshToken,
  };
}
```

### Work Item 2.5: Remove PII from JWT Payload (MAJ-08)

**Goal:** The JWT access token payload currently includes `email` and `role` fields. This is PII in a token that cannot be revoked (until expiry). Only `sub` (user ID) should be in the token; other data should be fetched from the database.

**Fix:** Remove `email` from `generateAccessToken()` payload. Remove `email` and `role` from the JWT interface/type if defined separately.

#### Files to Modify

| File | Required Changes |
|------|-----------------|
| `backend/src/auth/auth.service.ts` | In `generateAccessToken()`: remove `email` from the payload object. Keep only `sub: user.id`. If any code or guard reads `email` from the JWT payload, update to fetch from DB via `UsersService.findById()` instead. |

#### Implementation

```typescript
// auth.service.ts — updated generateAccessToken
private generateAccessToken(user: User): string {
  const payload = { sub: user.id };  // ← removed email
  return this.jwtService.sign(payload, {
    secret: this.configService.get<string>('JWT_SECRET'),
    expiresIn: this.configService.get<string>('JWT_ACCESS_EXPIRATION_MS', '15m'),
  });
}
```

**Impact check:** The `JwtStrategy` (line 14-15) extracts `payload.sub` for DB lookup — no change needed. The `CurrentUser` decorator reads `request.user` which is populated by `JwtStrategy.validate()` — no change needed.

#### Test Strategy

### Work Item 2.6: Fix O(n) Logout to O(1) (MAJ-16)

**Goal:** `SessionService.revokeAllSessions()` currently iterates all user sessions with O(n) individual `delete()` calls. Replace with a single `delete({ userId })` call.

Additionally, `AuthService.logout()` iterates all sessions and compares raw tokens — O(n) scan. Replace with `sessionService.findByRefreshTokenHash()` for direct DB lookup.

#### Files to Modify

| File | Required Changes |
|------|-----------------|
| `backend/src/auth/session.service.ts` | Add `findByRefreshTokenHash(hash: string): Promise<Session \| null>`. Update `revokeAllSessions(userId)` to use `delete({ user: { id: userId } })` instead of iterating. |
| `backend/src/auth/auth.service.ts` | In `logout()`: hash the incoming token, then call `sessionService.findByRefreshTokenHash(hash)` for O(1) lookup instead of iterating all sessions. |
| `backend/src/auth/__tests__/session.service.spec.ts` | Add test for `findByRefreshTokenHash`. Update `revokeAllSessions` test. |
| `backend/src/auth/__tests__/auth.service.spec.ts` | Update logout test for direct lookup pattern. |

#### Implementation

```typescript
// session.service.ts — added findByRefreshTokenHash
async findByRefreshTokenHash(hash: string): Promise<Session | null> {
  return this.sessionRepo.findOne({ where: { refreshToken: hash } });
}

// session.service.ts — updated revokeAllSessions (was O(n), now O(1))
async revokeAllSessions(userId: string): Promise<void> {
  await this.sessionRepo.delete({ user: { id: userId } });
}
```

```typescript
// auth.service.ts — updated logout (was O(n) scan, now O(1) lookup)
async logout(userId: string, sessionToken?: string): Promise<void> {
  if (sessionToken) {
    const tokenHash = this.tokenHashService.hash(sessionToken);
    const session = await this.sessionService.findByRefreshTokenHash(tokenHash);
    if (session) {
      await this.sessionService.revokeSession(session.id, userId);
    }
  }
}
```
